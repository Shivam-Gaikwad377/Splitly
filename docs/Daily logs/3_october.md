# Splitly Backend — Daily Development Log

**Date:** 3 October 2026  
**Focus:** CI Optimization, Test Coverage, and Dependency Security

## Goal

Continue hardening the Splitly backend CI pipeline after the initial GitHub Actions setup by improving execution efficiency, measuring test coverage, and adding automated dependency security checks.

The goal was to make CI verify not only that the backend builds and tests pass, but also that the dependency tree is secure and the existing test suite provides measurable coverage.

---

## What We Did

### 1. Added npm Dependency Caching

Updated the GitHub Actions Node.js setup to use npm caching:

```yaml
- name: Setup Node.js
  uses: actions/setup-node@v7
  with:
    node-version: "24"
    cache: "npm"
```

### Why We Did It

Previously, every CI run had to download npm packages again.

The cache allows GitHub Actions to reuse npm's package cache between runs, reducing unnecessary dependency downloads while keeping `npm ci` as the actual dependency installation mechanism.

The important distinction was:

```text
Cache
→ avoids repeatedly downloading packages

npm ci
→ installs the exact dependency tree from package-lock.json
```

We intentionally kept `npm ci` because reproducible dependency installation is more important than simply making the pipeline faster.

---

### 2. Added Test Coverage

Installed the Vitest V8 coverage provider:

```bash
npm install -D @vitest/coverage-v8
```

Created `vitest.config.ts` and configured:

```text
Provider: V8
Coverage scope: src/**/*.ts
Excluded:
- server entry point
- database seed scripts
- TypeScript type declarations
- empty utility files
Reporters:
- terminal
- HTML
```

Added the npm script:

```json
"test:coverage": "vitest run tests/integration --coverage.enabled"
```

### Why We Did It

Passing tests only tell us that the defined test cases succeeded.

Coverage tells us which parts of the application were actually executed by those tests.

The first meaningful baseline showed:

```text
Statements: 92.96%
Branches:   79.62%
Functions:  91.30%
Lines:      92.96%
```

After adding targeted tests, the baseline improved to:

```text
Statements: 95.31%
Branches:   81.48%
Functions:  100%
Lines:      95.31%
```

We decided not to force coverage to 100% because coverage is a diagnostic metric rather than a quality score. The remaining gaps are primarily defensive and error-handling paths.

### 3. Added Three Behavior-Driven Integration Tests

Added tests for:

#### Root endpoint

```text
GET /
→ 200
→ backend health response
```

This covered the previously unexecuted root endpoint.

#### Unknown route

```text
GET /unknown-route
→ 404
→ ROUTE_NOT_FOUND
```

This verifies the application's `notFoundMiddleware`.

#### Unverified email login

```text
POST /auth/login
→ unverified user
→ 403
→ EMAIL_NOT_VERIFIED
```

The test also restores the user's verified state in a `finally` block so that one failing test cannot contaminate subsequent tests.

### Why We Did It

The goal was not to create artificial tests simply to increase the coverage percentage.

The tests cover real application behavior and security rules that should work correctly even outside of coverage analysis.

### 4. Eliminated Duplicate Test Execution in CI

Initially the workflow executed:

```text
npm run test:integration
```

and then:

```text
npm run test:coverage
```

This meant the same integration tests were executed twice.

We changed CI so that it now runs only:

```yaml
- name: Run integration tests with coverage
  run: npm run test:coverage
```

### Why We Did It

Running the same tests twice wastes CI execution time and resources without providing additional verification.

The optimized flow is:

```text
Integration tests
        +
Coverage collection
        ↓
One test execution
```

This was an important CI optimization lesson: adding more steps is not automatically better; repeated work should be removed where possible.

---

### 5. Prevented Coverage Artifacts from Being Committed

Added the generated coverage output to `.gitignore`:

```gitignore
coverage/**
```

### Why We Did It

The coverage directory is generated output, not source code.

The repository should contain:

```text
vitest.config.ts
package.json
package-lock.json
```

but not generated coverage artifacts.

This keeps the repository clean and ensures that the coverage report is regenerated by developers or CI when needed.

### 6. Added Dependency Security Auditing

Ran:

```bash
npm audit
```

Result:

```text
0 vulnerabilities
```

Then added the security audit to GitHub Actions immediately after `npm ci`:

```yaml
- name: Security audit
  run: npm audit
```

### Why We Did It

The dependency tree is part of the application's attack surface.

The CI pipeline should automatically detect known dependency vulnerabilities rather than relying only on a developer remembering to run an audit locally.

The resulting flow became:

```text
npm ci
   ↓
npm audit
   ↓
build
   ↓
PostgreSQL
   ↓
integration tests + coverage
```

We deliberately used `npm audit` rather than `npm audit fix`.

CI should detect security issues; it should not silently modify the project's dependency tree.

## What I Learned

### CI Caching

Caching should optimize repetitive work without replacing deterministic dependency installation.

```text
Cache → speed
npm ci → reproducibility
```

### Test Coverage

Coverage measures which parts of the code are exercised by tests.

It does not prove that the tests are high quality.

The current baseline is:

```text
95.31% statements
95.31% lines
100% functions
81.48% branches
```

### Branch Coverage

Branch coverage exposed decision paths that ordinary line coverage can hide.

This helped identify untested authentication and error-handling paths.

### Integration Testing and Local Infrastructure

The integration tests depend on PostgreSQL.

When PostgreSQL was not running locally, the tests failed with connection-refused errors before the actual test cases could execute.

CI avoids this dependency problem by creating PostgreSQL as a GitHub Actions service container.

### CI Optimization

Running tests once with coverage is better than running the same integration suite twice.

### Dependency Security

`npm audit` provides an automated check for known vulnerabilities in the dependency tree.

A clean audit today does not mean dependencies will remain secure forever, which is why the check belongs in CI.
